# 1.3.16

Module のアクセス権の判定を整理しました。
既存アプリの動作が変化する可能性がある項目の一覧です。

---

## 1. 読み取り権限のないユーザーは既存データを更新・削除できなくなりました

読み取りの条件 (`UserReadCondition`) を満たさないユーザーの更新・削除を、サーバーが拒否するようになりました。

```
変更前: 書き込みの条件だけを見ていたため、
        「読み取りの条件は満たさないが書き込みの条件は満たす」ユーザーは更新・削除ができた
変更後: 更新・削除は読み取りの条件も必要
```

画面からは元々その操作ができなかったため、通常の操作では変化しません。
スクリプトから `Module.Submit()` を呼んでいた場合は影響を受けます。

**書き込みの条件は、読み取りの条件を満たすユーザーの範囲内で書いてください。**
例えば読み取りを「部署A」、書き込みを「管理者」にしていて、管理者が部署Aに属さない場合、その管理者は更新・削除ができなくなります。
この場合は書き込みの条件を「管理者かつ部署A」あるいは読み取りの条件に管理者を含める形に直してください。

## 2. ListField の洗い替えもアクセス権のチェック対象になりました

`ListField` の洗い替え (行を全件削除して再登録するモード) で行われる削除が、
行モジュールのアクセス権のチェック対象になりました。行モジュールに条件を設定していない場合は影響ありません。

**ユーザーによる書き込みの認可 (`UserWriteCondition`)**

```
変更前: 洗い替えの削除は書き込みの条件のチェックを通っていなかった
        (書き込み権限のないユーザーでも洗い替えで行を削除できた)
変更後: 書き込みの条件を満たさないユーザーは洗い替え保存自体が失敗する
```

**データによる書き込みの認可 (`DataWriteCondition`)**

```
変更前: 書き込み条件を満たさない行 (編集できないはずの行) まで削除されていた
変更後: 書き込み条件を満たさない行は削除対象から外れ、削除されずに残る
```

こちらはエラーにはしていません。洗い替えの削除対象は検索条件で暗黙に決まるため、
拒否にするとデータ条件付きモジュールの正常な洗い替え保存が成立しなくなるからです。

**この変更で、洗い替え後のデータの見え方が変わります。**
条件外の行が残るため、「残った条件外の行」と「入れ直した現在の行」が並ぶ状態になり得ます。
編集できない行が保護される方向の変更ですが、洗い替えを前提にしたデザインでは見え方が変わります。
書き込み条件付きのモジュールを完全洗い替えしている場合は、条件外の行が残る前提で設計を見直してください。

## 3. Standalone の SQL 実行に書き込み権限が必要になりました

ExecuteSqlField の実行タイミングが `Standalone` のものを実行するとき、
そのモジュール (と、ListField の行モジュールで実行されるもの) の書き込みの条件を満たす必要があります。

```
変更前: アプリにアクセスできるユーザーなら誰でも実行できた
変更後: 書き込みの条件を満たすユーザーだけが実行できる
```

書き込みの条件を設定していないモジュールでは影響ありません。

SQL 文の内容は Codeer.LowCode.Blazor からは判断できないため、
**データによる認可 (行の条件) は Standalone の SQL には効きません。項目単位の権限も SQL が触る列には効きません。**
行や項目で絞りたい場合は SQL 側の WHERE で絞ってください
(ログインユーザーの値を持つフィールドをモジュールに置き、パラメータとして SQL に渡します)。

また、権限フィールドで ExecuteSqlField を対象にすると「その SQL を実行できるか」を SQL ごとに制御できるようになりました。

```
変更前: 権限フィールドの対象に ExecuteSqlField を指定しても何も起きなかった
変更後: 書き込みの条件を満たさないユーザーは、その SQL を含む Standalone の実行が失敗する
```

集計など読み取り目的で Standalone を使っていて、そのモジュールの書き込みを制限している場合は、
QueryField への置き換えを検討してください。

## 4. Query モジュールにデータによる認可（行の条件）が効かなくなりました

QueryField を持つモジュールでは、「読み取りできる行の条件」を設定しても行が絞られなくなりました。

```
変更前: クエリの結果に対する外側の絞り込みとして働いていた
        (集計するクエリでは行は絞られるが、集計された値には他の行が混ざっていた)
変更後: 一切適用されない。設定されているとデザインチェックが知らせる
```

クエリの行は SQL 自身が定義するものなので、行の絞り込みも SQL の WHERE 句に書いてください。
ユーザーごとに絞る場合は、新しく追加された予約パラメータ **`current_user_id`** が使えます
（サーバーが常にログインユーザーの Id を渡すため、利用者が変更できず権限として使えます）。
→ [QueryField](../db/query_field.md)

## 5. リンク先・埋め込み先のモジュールにも読み取りの認可が効くようになりました

これまで、リンクの表示値や埋め込みリスト（ページングなしの ListField・ModuleField）は、
リンク先・埋め込み先モジュールの認可を通らずに取得されていました。次のように変わります。

**ユーザーによる認可（読み取り）を満たさないモジュールのデータは、他の画面に同梱されても見えません。**

```
変更前: リンク列・リンクの表示テキスト・埋め込みリストは、リンク先モジュールの
        読み取り条件を満たさないユーザーにも見えていた
変更後: その部分だけ空になる (親のデータ自体は今までどおり見える)。
        読めないモジュールの項目を検索条件・ソートに使うとエラーになる
```

**データによる認可（行の条件）は、埋め込みリスト・埋め込みモジュールに効くようになりました。**

```
変更前: ページングなしの ListField は、行の条件を満たさない行も表示していた
        (ページングありの ListField では絞られており、設定によって挙動が違っていた)
変更後: どちらも同じように絞られる
```

リンクの表示値（リンク列・表示テキスト）には行の条件は効きません。
隠したい場合は権限フィールドでリンクの項目を対象にしてください（デザインチェックが知らせます）。

## 6. 読み取り権限のないユーザーでも新規作成ができるようになりました

読み取りの条件を満たさないユーザーでも、書き込みの条件を満たしていれば新規作成ができます。

```
変更前: 読み取りの条件を満たさないユーザーは、新規作成の画面も参照専用になり入力できなかった
変更後: 新規作成の画面を開いて入力・保存できる
```

新規作成は書き込む先のデータを指定しない操作のため、読み取りの条件を要求しません。
これを利用すると、投稿した本人にも内容を見せない投函フォーム (問い合わせ受付・申請提出・匿名アンケート) を作れます。
→ [認証・認可](../authorization/authorization.md)

保存した後はそのデータを読み戻せないため、そのデータの画面へは移動せず、入力した内容がフォームに残ります。

読み取りの条件を満たさないユーザーに新規作成をさせたくない場合は、書き込みの条件も設定してください。
